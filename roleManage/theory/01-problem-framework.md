# 01 · 问题框架：权限在回答什么

> 术语见 [glossary.md](./glossary.md)。本章是全书的地基：模型再多，都在回答同一类问题。

## 1. 学习目标

读完本章，你应能：

1. 用四元组写出任意一次权限判定句  
2. 区分**功能权限**与**数据权限**，并指出混用的典型后果  
3. 说明权限、角色、用户三者关系（概念层，不深入 RBAC96）  
4. 按粒度阶梯判断「首期做到哪一层」以及成本含义  
5. 区分认证与授权  
6. 在写方案前，用最小澄清清单自检是否「问题已定义清楚」  

## 2. 为什么先有框架，再谈模型

很多人一上来问：「我们用 RBAC 还是 ABAC？」  
更致命的问题往往是：**还没说清楚系统要判定的是什么。**

- 选错模型 → 可以换、可以组合  
- **答错问题** → 表结构、角色、接口鉴权会整体歪掉，返工成本极高  

因此教材约定顺序：

```
问题框架（本章）→ 演进与模型 → 考量与决策 → 交付物 →（以后）工程实现
```

**经验法则：** 答不清本章末尾的澄清清单，就不要进入框架选型与建表。

## 3. 四元组：一次判定的最小完整描述

### 3.1 定义

任意一次授权判定，都可以写成：

> **Subject** 对 **Object** 执行 **Action**，在 **Context** 下，是否允许？

| 维度 | 含义 | 典型例子 | 易漏点 |
|------|------|----------|--------|
| **Subject（主体）** | 谁在请求 | 员工、外包账号、服务账号、第三方应用 | 只想到「人」，忘了系统集成账号 |
| **Object（客体）** | 碰的是什么 | 菜单、API、某条订单、某文件 | 混淆「功能」与「某一条业务数据」 |
| **Action（操作）** | 做什么 | view / create / export / approve | 把「能进页面」当成「能导出」 |
| **Context（环境）** | 在什么条件下 | 租户、部门、时间、IP、设备 | 首期常可简化，但要**显式声明简化了什么** |

四元组是**问题描述语言**，不是某个模型的私有概念。DAC/RBAC/ABAC/UCON 都在用不同方式填这四个槽。

### 3.2 最小例子（贯穿后文）

场景：销售张三，工作日，在公司内网，想导出「销售一部」的订单列表。

| 维度 | 取值 |
|------|------|
| Subject | 用户张三（主部门=销售一部，角色含「销售」） |
| Object | 订单集合 / 导出接口所代表的资源 |
| Action | export |
| Context | 工作日、内网；部门=销售一部 |

后续章节会问：  
- 有没有 `order:export` 这类**功能权限**？  
- 即使有，数据是否只应落在**本部门**（数据权限）？  
- 若还要求「导出前勾选同意」或「会话中可吊销」，则触及 UCON 思维。

### 3.3 判定在系统中的位置（概念）

```
认证（你是谁）→ 得到 Subject
     ↓
收集 Object + Action + Context
     ↓
授权判定（是否允许）→ 允许 / 拒绝
     ↓
（可选）审计：记下这次判定与操作
```

本章聚焦**授权**；认证只要求你分得清边界（见 §7）。

## 4. 必须拆开的两层：功能权限 vs 数据权限

### 4.1 定义

| 层 | 问题 | 例子 | 常见建模 |
|----|------|------|----------|
| **功能权限** | 能不能用这个能力 | 是否显示「导出」；能否调用导出 API | 权限码 + 角色（RBAC） |
| **数据权限** | 能作用到哪些数据 | 仅本人 / 本部门 / 本租户 / 全量 | 范围规则（轻量 ABAC）或查询过滤 |

两层同时为真，请求才真正「做成」：

```
允许 = 具备功能权限 ∧ 数据落在允许范围内
（对象分享场景还可能：∨ ACL/关系授予）
```

### 4.2 为什么必须拆开

**反例：把数据范围写进角色名**

- `销售_华东_可导出`  
- `销售_华北_可导出`  
- `销售_华东_仅本人_可导出`  
→ 部门 × 范围 × 操作 组合爆炸 = **角色爆炸**。

**正例：拆开**

- 角色「销售」拥有 `order:export`（功能）  
- 张三的数据范围 = `DEPT`（数据）  
→ 人换部门只改归属/范围，不必新建角色。

### 4.3 概念辨析

| 说法 | 对吗 | 说明 |
|------|------|------|
| 「给销售角色」 | 通常指功能权限包 | 完整说法还应问数据范围 |
| 「本部门可见」 | 数据权限 | 单独成立时仍要有 view 功能权 |
| 「菜单能看见就能导出」 | 危险 | 菜单是展现，导出是另一操作 |

## 5. 权限、角色、用户（概念预告）

详细理论见 [models/03-rbac.md](./models/03-rbac.md)。此处只建立词汇，避免后文失语。

| 概念 | 定义 | 比喻 |
|------|------|------|
| **权限（Permission）** | 原子能力，常写成 `资源:操作` | 一把钥匙能开的锁 |
| **角色（Role）** | 权限的打包，对应职责 | 钥匙串 / 岗位工具箱 |
| **用户（User）** | 被指派角色的主体 | 拿着钥匙串的人 |

```
用户 ──绑定──► 角色 ──拥有──► 权限
```

**纪律（后面反复出现）：**

- 角色是**权限包**，不是部门别名  
- 部门/租户优先描述**数据范围**  
- 主路径应是「人绑角色」，而不是「人直接绑大量权限」  

## 6. 粒度阶梯与成本

### 6.1 阶梯

```
模块 → 功能/菜单 → 操作(CRUD/导出/审批) → 字段 → 行/对象实例
         ▲                    ▲
    过粗，难控              首期推荐停靠点
                                              ▲
                                    更细 → 更靠近 ABAC / ACL / ReBAC
```

| 粒度 | 含义 | 成本直觉 |
|------|------|----------|
| 模块 | 「能进订单模块」 | 便宜，但过粗 |
| 操作 | `order:view` / `order:export` | **推荐默认** |
| 字段 | 能看金额不能看手机号 | 高：规则与测试暴涨 |
| 行/实例 | 这一单能否给张三看 | 高：常要 ACL/ReBAC 或强过滤 |

### 6.2 启动建议

1. 功能权限先定到**操作级**  
2. 数据用**范围规则**（SELF/DEPT/…），不要为每行建角色  
3. 字段级、任意对象 ACL：**首期默认不做**，除非有硬需求并写入「做」的清单  

## 7. 认证 ≠ 授权

| | 认证 Authentication | 授权 Authorization |
|--|---------------------|----------------------|
| 问 | 你是谁？ | 你能做什么？ |
| 失败表现 | 未登录、Token 无效 | 已登录但 403 / 无按钮 |
| 常见手段 | 密码、SSO、JWT 签发 | 角色、策略、ACL… |

登录成功**只说明 Subject 已知**，不说明拥有任何业务权限。  
教材后文默认：Subject 已认证，讨论授权模型。

## 8. 启动时最小澄清清单

写权限方案前，至少书面回答：

| # | 问题 | 答不清时的典型后果 |
|---|------|---------------------|
| 1 | Subject 有哪些类型？（人 / 服务 / 外部系统） | 上线后对接账号「临时开上帝权限」 |
| 2 | Object 以功能为主，还是也有实例分享？ | 用角色硬撑分享，或用 ACL 硬撑岗位 |
| 3 | 是否有多租户 / 组织树 / 数据归属？ | 数据权限事后打补丁，接口到处 if |
| 4 | 只要请求时判定，还是使用过程仍要管？ | 漏掉吊销、配额、同意等需求 |
| 5 | 首期明确**不做**到哪一层粒度？ | 范围蔓延，永远「再加一点」 |

答不清 → **停**。先找业务把问题定义清楚，再进 [02-model-evolution.md](./02-model-evolution.md)。

## 10. 小结与自测

### 小结

- 权限问题的标准句式是四元组判定句。  
- 功能权限与数据权限必须分开建模。  
- 角色打包权限；部门/租户管范围。  
- 粒度默认停在操作级；更细要付治理成本。  
- 认证解决身份，授权解决能力。  
- 问题没定义清，不要选型。  

### 自测

1. 用四元组描述：「客服李四查看工单 T-99」。缺了哪一维时最容易设计出漏洞？  
2. 「运营_华南_可导出」这种角色名坏在哪里？如何拆成功能 + 数据？  
3. 用户能打开订单列表页，是否等于能调用导出接口？为什么？  
4. 认证成功但导出返回 403，问题出在哪一层？  
5. 写出你当前（或虚构）项目的澄清清单五问答案（可简答）。  

**要点：** 1）Context/数据归属常被漏；2）范围塞进角色名 → 爆炸；3）菜单 ≠ 操作权；4）授权；5）主观题，对照 §8。
