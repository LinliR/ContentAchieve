# 05 · 使用控制（Usage Control / UCON）

## 1. 学习目标

读完本章，你应能：

- 说明 UCON 相对传统访问控制多出来的问题域（使用全过程）  
- 用 ABC（Authorization / oBligation / Condition）描述一次受控使用  
- 解释持续性（ongoing）与可变性（mutability）为何重要  
- 把 UCON 当作需求检查表，而不是默认实现目标  

## 2. 历史背景与发展

传统模型（含常见的 RBAC/ABAC 用法）多回答：

> **在请求发生时**，是否允许这次访问？

数字版权、云资源计量、长时间会话、隐私同意、高风险操作的持续合规，提出了新问题：

- 允许之后，**使用过程中**条件变了怎么办？（付费到期、权限被撤、离开安全区）  
- 使用前/中是否必须履行**义务**？（同意协议、写审计、加水印）  
- 主体/资源属性是否在使用中**被更新**并反过来影响后续是否继续允许？（额度递减）  

Park 与 Sandhu 等提出的 **UCON**（Usage Control）把「访问控制」扩展为「使用控制」，试图统一并覆盖 DAC/MAC/RBAC/ABAC 等讨论过的能力，并显式加入义务与持续决策。

对教材与项目：UCON 的价值首先是**概念完备性**——帮你发现需求是否已超出「进门鉴权」。

## 3. 核心理论

### 3.1 基本定义

**UCON**：关注数字对象在使用前、使用中（及与义务相关的使用后要求）是否持续满足授权、义务与条件；属性可以可变，决策可以持续。

### 3.2 核心概念：ABC

| 字母 | 名称 | 含义 |
|------|------|------|
| **A** | Authorization 授权 | 传统意义上的允许/拒绝规则 |
| **B** | oBligations 义务 | 必须履行的动作（同意、通知、记录、支付…） |
| **C** | Conditions 条件 | 与环境相关的约束（时间、系统状态等），常独立于主客体属性 |

### 3.3 时间与决策：pre / ongoing / post

| 时机 | 含义 |
|------|------|
| **pre** | 使用开始前检查授权/义务/条件 |
| **ongoing** | 使用过程中持续或周期检查；失败则中止 |
| **post** | 与使用后义务相关的要求（教材上常结合义务讨论） |

### 3.4 可变性（Attribute Mutability）

属性可在决策前后被更新，例如：

- 下载次数 `remaining = remaining - 1`  
- 会话风险分上升 → 后续 ongoing 检查失败  

这使 UCON 能描述「越用越少」「越用越严」的策略。

### 3.5 最小例子

在线课程视频：

- **pre-Authorization**：用户有有效订阅  
- **pre-Obligation**：同意使用条款  
- **Condition**：仅在允许的地区  
- **ongoing**：订阅仍有效；否则中断播放  
- **可变属性**：今日已看时长累加，超过限额则后续拒绝  

## 4. 变体与扩展

UCON 文献中有多种「模型切片」（哪些决策点启用 A/B/C，是否 ongoing，是否可变）。教材不要求记忆全部编号，但要能根据需求拼装：

- 只要 pre-Authorization → 退回传统访问控制  
- 要同意条款 → 加 Obligation  
- 要到期踢下线 → 加 ongoing + Condition/Authorization  
- 要计量 → 加可变属性  

## 5. 优势

- **问题域完整**：覆盖现代数字服务真实痛点  
- **统一视角**：可容纳此前多种模型的讨论  
- **迫使产品想清「使用中」**：避免只做登录鉴权却忽略吊销与义务  

## 6. 不足与局限

1. **工程完整落地重**：持续监控、属性一致性、中止动作都贵  
2. **概念负担高**：团队易误解为「又一个 RBAC」  
3. **与业务系统匹配度**：多数 CRUD 后台并不需要完整 UCON  
4. **测试与证明复杂**：ongoing 与可变属性使状态空间变大  
5. **过度引用风险**：用 UCON 包装普通鉴权，失去沟通价值  

## 7. 在演进链中的位置

- **相对 ABAC/RBAC**：从「请求时」扩展到「使用时」，并系统化义务与可变性  
- **不是简单下一代产品名**：更像统一框架与需求透镜  
- **今日用法**：检查清单 + 局部机制（Token 吊销、配额、同意横幅），而非必建 UCON 中间件  

## 8. 适用与不适用

| 更适用（思维或局部机制） | 更不适用 |
|--------------------------|----------|
| DRM、计量云 API、长会话高风险操作 | 标准企业内部 CRUD 后台作为整模目标 |
| 需要使用中吊销、额度、强制同意 | 团队只需要菜单与接口权限 |
| 合规要求「持续控制」 | 用 UCON 名词替代清晰的 RBAC 设计 |

## 9. 概念辨析

| 概念 | 辨析 |
|------|------|
| UCON vs ABAC | ABAC 提供属性策略表达；UCON 还强调义务、持续、可变——ABAC 策略可用于 UCON 的 A/C 部分 |
| 义务 vs 条件 | 义务是「必须做的事」；条件是「环境必须满足的状态」 |
| Token 过期 vs ongoing | 过期是粗粒度机制；ongoing 是持续策略评估的思想，可用过期近似，但不等同 |

## 10. 小结与自测

### 小结

UCON 把访问控制升级为使用控制：授权、义务、条件，并可在使用中持续作用、属性可变。它对项目最大的价值是识别「进门之后还要不要管」；完整实现不是默认选项。

### 自测

1. 用 ABC 拆解「导出客户数据前必须勾选同意，且仅内网可导出」。  
2. 举一个必须 ongoing 的例子；再举一个 pre 一次就够的例子。  
3. 为何说多数业务后台「需要 UCON 思维，但不需要 UCON 平台」？  

**要点**：1）A=有导出权；B=同意；C=内网；2）订阅视频中途到期 / 点一次查询接口；3）检查清单指导局部设计即可。
