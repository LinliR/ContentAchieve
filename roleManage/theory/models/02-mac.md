# 02 · 强制访问控制（Mandatory Access Control / MAC）

## 1. 学习目标

读完本章，你应能：

- 说明 MAC 中「强制」强制在何处，与 DAC 的本质差别  
- 描述安全标签（密级）与「不上读 / 不下写」等典型规则直觉  
- 解释为何 MAC 在军政高安全场景重要，却很少作为业务系统唯一模型  
- 识别需求里何时出现「MAC 信号」  

## 2. 历史背景与发展

DAC 的灵活带来扩散与不可控。高安全领域（军事、情报、部分政府系统）需要另一种承诺：

> **即使是属主，也不能违反系统安全策略。**

于是出现强制访问控制：系统根据**安全策略与安全属性（标签）**决定访问，主体不能随意改写这些判定规则。

历史上常与多级安全（MLS）、Bell–LaPadula（机密性）、Biba（完整性）等模型一并讨论。对教材而言，不必陷入公式细节，抓住两点即可：

1. 主体、客体带**标签**  
2. 是否允许由**系统策略**比较标签决定，而非属主心情  

MAC 补了 DAC 的「全局强制」缺口；代价是灵活性急剧下降——这也解释了为何企业管理主线后来走向 RBAC，而不是人人上密级。

## 3. 核心理论

### 3.1 基本定义

**MAC**：访问是否允许由系统强制安全策略决定；该策略基于主体与客体的安全属性（如密级、类别），普通用户（含属主）不能擅自变更策略后果。

### 3.2 核心概念

| 概念 | 含义 |
|------|------|
| 安全标签 / 密级 | 如公开 < 内部 < 秘密 < 机密 |
| 安全策略 | 规定标签之间何种读写关系合法 |
| 强制 | 用户不能通过「分享」绕过策略 |
| 机密性导向 vs 完整性导向 | 防泄露 vs 防篡改（不同经典模型侧重不同） |

### 3.3 判定如何发生（直觉版）

1. 取 Subject 的安全属性、Object 的安全属性  
2. 取 Action（读/写等）  
3. 用系统策略比较属性（例如：读要求主体密级不低于客体；写可能禁止「高密级写到低密级」以防泄露）  
4. 允许或拒绝——**属主不能发一张「例外分享」来推翻**（除非策略明确提供受控例外且由安全管理员配置）  

### 3.4 最小例子

- 文件 F 标为「机密」，用户 U 标为「内部」  
- 策略：读要求主体密级 ≥ 客体密级 → U **不能读** F  
- 即使用户「拥有」F 的业务意义，也不能擅自把 F 改成「公开」除非具备安全管理员权限与合规流程  

## 4. 变体与扩展

- **多级安全（MLS）**：线性密级  
- **多范畴 / 隔间（categories/compartments）**：密级 + 类别集合  
- **类型强制（Type Enforcement）** 等机制：用类型与策略约束流转（如 SELinux 思想）——同属「系统强制」家族，细节不同  
- **与 DAC 组合**：许多系统是 MAC 打底 + DAC 再收紧（先强制后自主）  

## 5. 优势

- **防扩散能力强**：授权不能随意流到低密级或错误范畴  
- **策略中心化**：安全管理员可理解、可审计的全局规则  
- **适合强隔离与高合规**  

## 6. 不足与局限

1. **过刚**：业务例外多时，标签与策略维护成本极高  
2. **组织岗位表达弱**：MAC 不直接回答「运营能不能导出订单」  
3. **可用性差**：错误标签导致大规模无法办公  
4. **标签治理本身是难题**：谁定密级、谁降密、如何定期审定  
5. **对互联网业务产品通常过重**：除非有明确等保/密级硬性要求  

## 7. 在演进链中的位置

- **相对 DAC**：用强制策略补全局可控与防泄露  
- **留给 RBAC 的缺口**：缺少面向企业岗位与权限包的管理模型  
- **今日位置**：高安全系统的底座思想；业务系统偶发「租户强隔离」「密级文件」是局部 MAC 信号，不等于整站 MAC  

## 8. 适用与不适用

| 更适用 | 更不适用 |
|--------|----------|
| 军政、机密信息系统 | 唯一模型支撑普通 SaaS 后台 |
| 强隔离、防泄密红线 | 快速变化的产品权限、频繁分享 |
| 已有安全标密制度的组织 | 尚无标密治理能力却强行上全站 MAC |

## 9. 概念辨析

| 概念 | 辨析 |
|------|------|
| MAC vs 「管理员说了算」 | 管理员配置的是**系统策略**；MAC 强调策略对普通属主不可违背，不是「谁官大谁授权」 |
| MAC vs 多租户隔离 | 租户隔离常像硬边界，可借鉴 MAC 精神，但实现上多是分区/属性条件，未必是经典密级模型 |
| 强制 vs 强制二因子 | 二因子是认证强度；MAC 是授权策略类别——不同层面 |

## 10. 小结与自测

### 小结

MAC 用系统强制标签策略换取强可控与防扩散，牺牲灵活性。它与 DAC 构成经典双极；业务权限主线并未停在 MAC，而是走向 RBAC。

### 自测

1. 「文件主人不能把机密文件改成可对外分享」体现了 DAC 还是 MAC？  
2. 为什么说 MAC 很难单独支撑 ERP 的岗位授权？  
3. 举一个「看起来像 MAC、其实只是租户字段过滤」的例子，并说明差别。  

**要点**：1）MAC；2）MAC 不建模角色—权限包；3）租户_id 条件是属性/边界，未必有强制标签体系与安全管理员策略。  

## 11. 延伸阅读

- Bell–LaPadula、Biba：机密性 / 完整性经典模型（知其侧重点即可）  
- 现代 OS 强制访问相关机制概述（如 SELinux 文档总览）——理解「类型强制」与密级模型是不同机制
