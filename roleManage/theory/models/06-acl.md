# 06 · 访问控制列表（Access Control List / ACL）〔旁支〕

## 1. 学习目标

读完本章，你应能：

- 说明 ACL 是什么，以及它与 DAC、访问矩阵的关系  
- 描述 ACE（条目）的一般形态  
- 指出 ACL 在对象级分享上的优势与规模化时的不足  
- 说明为何工程上常「RBAC + 少量 ACL」  

## 2. 历史背景与发展

在访问矩阵中，若**按客体列存储**授权，就得到 ACL：每个客体挂一张「谁可以做什么」的列表。  
操作系统、文件系统、协作文档产品大量采用这一形态，以致口语里常把 ACL 直接叫「权限」。

ACL 本身首先是**实现与数据结构视角**，策略上常服务于 **DAC**（属主维护列表），也可以由管理员中心化维护（此时「自主」色彩变弱）。  
在 RBAC 成为企业功能权限主流后，ACL 并未消失，而是退守到**实例级授权**战场。

## 3. 核心理论

### 3.1 基本定义

**ACL**：与某客体关联的授权条目列表；每条通常指定主体（或主体组）及允许/拒绝的操作。

### 3.2 核心概念

| 概念 | 含义 |
|------|------|
| ACL | 客体上的列表 |
| ACE | 列表中的一条：主体 + 权限 + 允许/拒绝 等 |
| 默认/继承 | 子对象从父容器继承 ACL（文件系统、网盘常见） |
| 显式拒绝 | 部分系统支持 deny 条目及优先级规则 |

### 3.3 判定如何发生

1. 定位 Object 的 ACL（及继承合并结果）  
2. 按系统规则匹配 Subject 与 Action（顺序、deny 优先等）  
3. 得到允许或拒绝  

### 3.4 最小例子

文档 Doc#42 的 ACL：

| 主体 | 权限 |
|------|------|
| Alice | 读、写 |
| 组:运营 | 读 |
| Bob | 读 |

Carol 不在列表中 → 不能访问（假设默认拒绝）。

## 4. 变体与扩展

- **POSIX ACL / NTFS ACL** 等：组、继承、特殊位  
- **分享链接**：可视为对「持有链接者」的特殊主体  
- **与 RBAC 叠加**：先过功能角色，再过对象 ACL  
- **ACL + 过期时间**：条目带 TTL，接近条件化  

## 5. 优势

- **对象级直观**：很适合「这篇文档给谁看」  
- **局部变更便宜**：改一个对象的列表即可  
- **用户可理解**：协作产品中的分享 UI 几乎就是 ACL 编辑器  

## 6. 不足与局限

1. **规模化差**：海量对象 × 长列表 → 存储与查询压力  
2. **主体变更痛苦**：人换岗/离职需扫过大量 ACL（或依赖组间接层）  
3. **全局策略弱**：与纯 DAC 类似的治理问题  
4. **与岗位权限重复建模**：用 ACL 表达「所有订单的导出权」是错误层级  
5. **继承与冲突规则复杂**：管理员难推理最终有效权限  

## 7. 在演进链中的位置

- **不是** DAC→MAC→… 的下一站，而是矩阵的列式实现 / 对象侧工具  
- **服务 DAC** 为主，也可被中心策略驱动  
- **与 RBAC**：功能用 RBAC，实例分享用 ACL，是稳定分工  

## 8. 适用与不适用

| 更适用 | 更不适用 |
|--------|----------|
| 文档、工单、单个资源的分享 | 全站功能权限的主模型 |
| 对象数量可控或有继承结构 | 每条业务行都挂长 ACL |
| 需要属主或协作者可见的授权 UI | 以岗位职责为中心的 ERP 权限 |

## 9. 概念辨析

| 概念 | 辨析 |
|------|------|
| ACL vs RBAC | 客体名单 vs 角色权限包；问题层级不同 |
| ACL vs ABAC | ACL 枚举主体；ABAC 用属性规则概括主体集合 |
| 组 ACL vs 角色 | 组进 ACL 仍是对象级授权；角色通常是全局功能授权 |

## 10. 小结与自测

### 小结

ACL 从访问矩阵的列存储而来，擅长对象级授权与分享，短于全局岗位治理与海量枚举。旁支地位不影响其在协作场景中的重要性。

### 自测

1. 为什么「给运营角色开订单导出」不该做成「每个订单一条 ACL」？  
2. 离职回收场景下，ACL 模型的痛点是什么？常用缓解手段？  
3. 「RBAC + ACL」各管哪一层？  

**要点**：1）功能级应用 RBAC；2）扫列表难 → 用组/中心身份生命周期；3）功能 vs 实例。
