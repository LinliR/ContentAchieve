02 · 模型演进：问题如何一步步变难

读完 01-problem-framework.md 再读本章。
各模型细节在 models/；本章只建立演进叙事与选型透镜。

1. 学习目标

读完本章，你应能：

  1. 默写主线 DAC → MAC → RBAC → ABAC → UCON，并说明每步「补了什么缺口」
  2. 解释：演进线是能力叙事，不是淘汰顺序，也不是实施顺序
  3. 指出 ACL、ReBAC、Capability 的旁支位置
  4. 用演进线判断一个需求大概停在哪一阶段（为决策章做准备）
  5. 区分「传统请求时访问控制」与 UCON「使用全过程」

2. 如何理解这条线

学术与教材常见写法：

DAC → MAC → RBAC → ABAC → UCON

正确理解：

是 不是
问题变难后，理论补能力 后面完全取代前面
帮助判断需求天花板 新项目必须从 UCON 做起
解释「为什么会出现下一代」 唯一存在的模型分类法

并存是常态。 今日业务系统常见：RBAC 打底 + 属性规则 + 少量 ACL，并不「落后」。

3. 演进在补什么（主叙事）

阶段 模型 核心矛盾（要解决的） 新问题（留给后代的）
经典 DAC 要灵活分享，属主说了算 权限扩散、弱全局治理
经典 MAC 要强制防泄露，策略不可被属主推翻 过刚，难贴业务岗位
组织化 RBAC 要按岗位打包权限，人变岗变可治理 静态；角色爆炸；难表达上下文
动态细粒度 ABAC 要用属性+策略表达动态条件 策略治理、可解释、测试成本
使用全过程 UCON 要管使用中：义务、持续检查、属性可变 概念重；完整工程落地少

3.1 各阶段一句话

  • DAC：主人说了算。
  • MAC：系统按标签/策略强制说了算。
  • RBAC：你是什么角色，就有什么权限包。
  • ABAC：当下属性与策略是否满足。
  • UCON：授权 + 义务 + 条件；可事前/事中；属性可变更。

3.2 缺口传递（建议默写）

DAC 灵活
  └─缺口→ 扩散与弱全局策略
MAC 强制
  └─缺口→ 过刚、不贴岗位
RBAC 岗位化
  └─缺口→ 静态、难上下文、难实例分享
ABAC 动态细粒度
  └─缺口→ 治理难；仍常偏「请求时」
UCON 使用全过程
  └─缺口→ 完整落地重；名词易被滥用

4. 两条经典线，再汇入企业线

更细的图景（避免以为历史是单车道）：

安全经典线：  DAC ⇄ MAC
企业管理线：       → RBAC →（常与 ABAC 混合）
动态细粒度：            → ABAC / ReBAC
使用全过程：                  → UCON
对象级分享：     ACL（常作为 DAC 实现形态，也可挂在 RBAC 上）
能力票证：       Capability（矩阵「行」视角，与 ACL「列」对称）
  • DAC/MAC：先回答「灵活 vs 强制」的安全经典问题。
  • RBAC：把重心拉到「组织与岗位」。
  • ABAC/UCON：再拉到「动态条件」与「使用过程」。

5. 传统访问控制 vs UCON

传统常见用法（DAC/MAC/RBAC/ABAC）：
  请求到来 → 判定一次 → 允许则本次（或会话内）用到底

UCON：
  请求到来 → 判定（可含义务）
           → 使用中可持续检查
           → 条件/属性变化可中止
           → 属性可在使用中被改写（如额度 -1）

因此：UCON 更像统一与扩展框架，不是「ABAC 换皮升级版」。
项目中：用 UCON 当检查清单（有没有义务？要不要 ongoing？），多数 CRUD 后台不必上 UCON 平台。

6. 旁支：为什么单列

旁支 判定看什么 为何不塞进主线第 N 代
ACL 该客体允许谁做什么 主要是访问矩阵的列式实现；常服务于 DAC，也服务实例分享
Capability 主体持有什么能力票 矩阵的行式实现；与 ACL 对称
ReBAC 关系路径是否成立 与 ABAC 同期偏应用的另一原语（关系图 vs 属性策略）

选型含义： 看到「分享给某人」「项目成员可读子文档」，先想 ACL/ReBAC，不要硬说「所以我们要上 UCON」。

7. 用演进线做「需求定位」（练习透镜）

把业务信号映射到阶段（粗定位，细选型见第 05 章）：

业务信号 粗定位
文件/文档由主人分享 DAC / ACL
密级、强制不能外传 MAC 思想
按岗位开菜单与按钮 RBAC
本部门/租户/工作日才能导出 RBAC + ABAC 思想
深层成员/父子继承可见性 ReBAC（或复杂 ACL）
播放中到期要停、同意后才能继续、额度用完断开 UCON 思想

练习： 华澄「澄单」案例（cases/m-tier-order-ops.md）应落在哪？
→ 主：RBAC；局部：ABAC 思想（部门范围）+ ACL（工单分享）；非 MAC/UCON 平台。

8. 对项目启动的三条纪律

  1. 用演进线判断能力上限：需求是否超出纯 RBAC？是否触及持续使用？
  2. 不用演进线当实施顺序：默认从 RBAC（或更简单）起步。
  3. 并存合法：组合不是「不纯粹」，而是工程常态。

错误示范：「最新是 UCON，所以我们要上 UCON。」
正确示范：「我们停在 RBAC+范围规则；出现 X 信号再评估 ABAC/UCON。」

9. 小结与自测

小结

演进线描述「问题如何变难、理论如何补洞」。
主线五模型 + 旁支 ACL/ReBAC/Capability。
UCON 把视野从「进门」扩到「使用全过程」。
选型时用它做定位透镜，用第 05 章做可执行决策。

自测

  1. 用「缺口传递」从 DAC 讲到 UCON（口头 1 分钟）。
  2. 为什么说「并存是常态」？举一个组合例子。
  3. ACL 为什么不是 DAC 的「下一代」？
  4. 「租户_id 过滤」是否等于已经做了 MAC？
  5. 给出一个需要 UCON 思维、但不需要 UCON 平台的例子。

要点： 2）如 RBAC+DEPT+ticket ACL；3）实现形态/旁支；4）否，缺强制标签体系；5）导出前同意勾选用产品流程即可。
