03 · 基于角色的访问控制（Role-Based Access Control / RBAC）

1. 学习目标

读完本章，你应能：

  • 画出用户—角色—权限关系，并解释为何不直接给用户绑大量权限
  • 概述 RBAC96 的核心思想（扁平 / 分层 / 约束）
  • 区分「角色」与「用户组」「部门」
  • 说明 RBAC 的优势、角色爆炸等局限，以及它为何成为业务系统默认根模型

2. 历史背景与发展

DAC 灵活但不治理；MAC 强制但不贴业务。1990 年代起，企业 IT 需要一种与岗位、职责对齐的授权方式：

人不直接拥有零散权限，而拥有角色；角色拥有权限包。人换岗 → 换角色；权变更 → 改角色一次，惠及所有人。

NIST 与 Sandhu 等人推动的 RBAC96 家族成为后续教材与产品的共同语言。RBAC 把访问控制从「安全标签思维」明显拉向「组织与业务授权思维」，是今日后台、ERP、运营系统的理论根。

其后 ABAC/UCON 等并不是要废除 RBAC，而是补其静态绑定与上下文不足；工程上最常见的是 RBAC 仍做主干。

3. 核心理论

3.1 基本定义

RBAC：权限授予角色；用户通过被指派角色而获得权限。访问判定的关键是：该用户的有效角色集合，是否覆盖所请求的权限。

3.2 核心概念

概念 含义
用户（User） 人或其他主体
角色（Role） 权限的命名集合，对应职责/岗位
权限（Permission） 对客体执行操作的许可（常写成资源+操作）
会话（Session） 用户激活部分角色的运行时上下文（理论模型中有，工程实现各异）
指派 UA：用户—角色；PA：角色—权限

核心关系：

User ——(UA)——► Role ——(PA)——► Permission
                 ▲
            可选：角色继承

3.3 判定如何发生

  1. 认证后得到用户 U
  2. 取 U 的有效角色集合 R（含继承展开）
  3. 取 R 的权限并集 P
  4. 请求的 Permission p ∈ P？允许 : 拒绝

（若引入会话，则只使用当前激活角色，体现最小权限运行时。）

3.4 最小例子

  • 权限：order:view、order:export、user:delete
  • 角色「运营」= {order:view, order:export}
  • 角色「管理员」= {order:view, order:export, user:delete}
  • 用户张三绑定「运营」→ 可导出订单，不能删用户

4. 变体与扩展（RBAC96 直觉）

教材常提四级（理解思想即可）：

层级 思想
核心 RBAC 用户—角色—权限、多对多指派
分层 RBAC 角色继承（经理拥有员工权限等）
约束 RBAC 互斥角色、基数限制等 → 支撑职责分离（SoD）
对称等扩展 关注权限—角色侧的管理对称性等（了解即可）

工程常见扩展（仍属 RBAC 家族讨论）：

  • 角色可启用/停用、生效时间窗（已开始沾环境属性）
  • 管理角色：谁能分配角色（行政权与业务权分离）

5. 优势

  • 与组织职责对齐，沟通成本低（「给运营角色」）
  • 变更经济：改角色权限一次，影响全体成员
  • 可审计：人—岗—权链条清晰
  • 实现与产品生态成熟，默认心智成本最低
  • 可通过约束表达职责分离

6. 不足与局限

  1. 角色爆炸：为覆盖细枝末节组合而疯狂建角色
  2. 静态性：难干净表达「仅本部门」「仅工作日」「仅本人数据」
  3. 角色设计本身是组织问题：角色乱，模型再对也救不了
  4. 继承使用不当：层级过深导致「实际权限」难以理解
  5. 不擅长对象级分享：把「这篇文档分享给张三」硬塞进角色会扭曲模型
  6. 与部门树混淆：用部门当角色，功能权与数据权搅死

7. 在演进链中的位置

  • 相对 DAC/MAC：提供企业可治理的岗位化授权，而不只靠属主或密级
  • 留给 ABAC 的缺口：上下文、属性、动态条件
  • 留给 ACL/ReBAC 的缺口：实例级分享与复杂关系
  • 今日位置：默认主模型；不足处用组合补，而不是轻易抛弃

8. 适用与不适用

更适用 更不适用（单独使用时）
后台、ERP、运营、内部工具 强动态条件为主的授权
岗位相对稳定、权限可枚举 海量对象各自不同的分享关系
需要清晰审计与职责分离 以密级强制为第一目标的系统（应 MAC+其他）

9. 概念辨析

概念 辨析
角色 vs 用户组 组常是「人的集合」；角色强调「权限包/职责」。实现上可能用同一张表，概念上应分开
角色 vs 部门 部门是组织归属与数据范围来源；角色是能力集合
权限 vs 菜单 菜单是权限的一种展现；接口/操作才是鉴权的真源
RBAC vs 「一个用户一个角色」 若角色与人一一对应，RBAC 退化，失去治理优势

10. 小结与自测

小结

RBAC 用角色连接人与权限，是企业权限管理的理论根与工程默认项。其局限集中在静态性、角色设计质量与对象级场景——应用组合模型补齐，而不是否定 RBAC。

自测

  1. 为什么「运营_华东_可导出_不可删」这类角色名可能是坏味道？更好的拆法是什么？
  2. 互斥角色想防止什么风险？举一例。
  3. 「只能看本部门订单」是纯 RBAC 能优雅表达的吗？缺口指向哪类模型思维？

要点：1）把数据范围塞进角色名导致组合爆炸 → 角色管功能，范围用规则；2）如出纳与会计分离防舞弊；3）不优雅，指向属性/数据范围（轻量 ABAC）。
