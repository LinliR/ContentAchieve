04 · 基于属性的访问控制（Attribute-Based Access Control / ABAC）

1. 学习目标

读完本章，你应能：

  • 说明 ABAC 的判定要素（主体/资源/操作/环境属性 + 策略）
  • 解释为何 RBAC 可视为 ABAC 的特例
  • 列举 ABAC 的表达力优势与治理代价
  • 区分「完整 ABAC 平台」与「RBAC + 轻量属性规则」

2. 历史背景与发展

RBAC 极大改善了岗位授权，但企业很快碰到：

  • 同一角色，数据范围却因部门、租户而异
  • 授权依赖时间、地点、设备、风险评分
  • 资源属性（灵敏度、归属项目）参与判定

若为每种组合建角色，会出现角色爆炸。于是策略转向：

不预先枚举所有角色组合，而用属性描述事实，用策略描述规则，请求时计算是否满足。

NIST 等对 ABAC 的系统化描述，使其成为「动态细粒度」的标准叙事。云、多租户、API 安全场景加速了它的普及。
需要强调：ABAC 不是 RBAC 的掘墓人；多数成功落地是 RBAC 管功能 + ABAC 思维管条件/数据范围。

3. 核心理论

3.1 基本定义

ABAC：是否允许访问，由策略基于主体、资源、操作及环境的属性求值决定。

3.2 核心概念

概念 含义
主体属性 部门、职级、角色列表、认证强度…
资源属性 所属部门、租户、灵敏度、创建者…
操作属性 读/写/导出/审批…（亦可当动作类型）
环境属性 时间、IP 网段、设备、地理位置…
策略（Policy） 规则集合；常含 permit/deny 与组合算法
策略决策点 / 执行点 理论分工：决定 vs 执行（工程对应 PDP/PEP 等）

3.3 判定如何发生

  1. 收集本次请求相关属性（或查询属性源）
  2. 选择适用策略
  3. 对策略求值（可能多规则冲突，需组合算法）
  4. 得到允许 / 拒绝（理想情况附原因）

3.4 最小例子

策略：

允许 当且仅当：
  subject.department == resource.department
  AND action == "view"
  AND environment.is_workday == true

张三（部门=华东）在工作日查看华东订单 → 允许
张三查看华北订单 → 拒绝
张三在周末查看华东订单 → 拒绝

4. 变体与扩展

  • RBAC 作为属性：subject.roles contains "ops" —— 兼容岗位于属性世界
  • PBAC（Policy-Based）：强调策略中心，与 ABAC 高度重叠，常混用称呼
  • 风险自适应：属性含风险分，动态提高要求（趋近持续评估）
  • 与 XACML 等策略语言：标准化策略表达（了解存在即可）

5. 优势

  • 表达力强：少建角色，多写规则即可覆盖组合条件
  • 细粒度自然：行级、上下文级条件是一等公民
  • 适应变化：组织属性变了，策略自动作用，不必重建角色矩阵
  • 适合多租户与复杂数据范围

6. 不足与局限

  1. 策略治理难：谁写、谁审、怎么测、怎么防止策略冲突
  2. 可解释性差：用户与管理员都可能不懂「为何拒绝」
  3. 属性质量依赖：属性错，授权全错；属性源延迟会造成窗口问题
  4. 性能与缓存复杂：每次请求聚合属性与求值有成本
  5. 过度设计风险：简单岗位系统上全量 ABAC，得不偿失
  6. 审计叙事变难：相对「角色变更日志」，策略变更影响面更隐晦

7. 在演进链中的位置

  • 相对 RBAC：补动态条件与细粒度，缓解角色爆炸
  • 留给 UCON 的缺口：仍偏「请求时判定」；对使用中持续控制、义务、属性可变性的系统化不足
  • 与 ReBAC：ABAC 用属性；ReBAC 用关系图——可表达重叠场景，建模偏好不同

8. 适用与不适用

更适用 更不适用
多租户、复杂数据范围 岗位极少且稳定的小后台（纯 RBAC 更省）
强上下文条件（时间/网络/设备） 团队无力做策略测试与变更管理
需要减少角色组合数量 把所有菜单权限都写成巨型策略（失去 RBAC 清晰性）

9. 概念辨析

概念 辨析
完整 ABAC vs 轻量属性规则 后者常是「RBAC + 部门/本人过滤器」；共享 ABAC 思想，未必上策略引擎
ABAC vs 业务里 if 语句 散落代码里的 if 不是可治理的 ABAC；ABAC 强调策略显式化与中心化
属性 vs 权限码 权限码是「能做什么」的符号；属性是「事实」；策略把二者连起来

10. 小结与自测

小结

ABAC 用属性与策略提供动态细粒度能力，是 RBAC 静态性的补完，而非默认替代。真正的成本在治理与可解释性；项目中优先采用「RBAC + 有限属性规则」。
