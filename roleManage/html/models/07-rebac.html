07 · 基于关系的访问控制（Relationship-Based Access Control / ReBAC）〔旁支〕

1. 学习目标

读完本章，你应能：

  • 说明 ReBAC 的核心思想：用主体—资源关系图推导授权
  • 举出「成员 / 拥有 / 父级」等关系如何传递权限
  • 对比 ReBAC 与 ABAC、ACL 在建模偏好上的差别
  • 识别协作、组织树、嵌套资源场景中的 ReBAC 信号

2. 历史背景与发展

当授权取决于「你和资源是什么关系」时，纯角色与纯属性枚举都会别扭，例如：

  • 项目成员可编辑项目下文档
  • 文件夹读者可读其子文件
  • 团队管理员可管理团队内所有资源

这类规则用关系图表达更自然：关系是一等公民，权限由关系路径推出。
学界用 ReBAC 概括这类模型；工业界则以 Google Zanzibar 等系统让「关系元组 + 命名空间配置」进入大规模生产。

ReBAC 与 ABAC 时间线上接近，同属细粒度动态家族，但建模原语不同：一个偏关系图，一个偏属性与策略语言。

3. 核心理论

3.1 基本定义

ReBAC：访问是否允许，取决于主体与客体（及中间对象）之间是否存在策略所认可的关系路径。

3.2 核心概念

概念 含义
关系元组 如 (文档42, parent, 文件夹7)、(文件夹7, viewer, 用户U)
关系类型 owner / editor / viewer / member / parent …
可达 / 推导 由配置的重写规则沿图搜索是否成立
命名空间配置 定义某种对象上「何关系蕴含何关系/何权限」

直觉图：

用户U --member--> 项目P --parent-- 文档D
配置：项目 member 可 view 其子文档
⇒ U 可 view D

3.3 判定如何发生

  1. 将请求表达为：Subject 是否对 Object 具有关系 R（如 viewer）
  2. 在关系图上按配置做可达性检查（可能含间接关系）
  3. 成立则允许

3.4 最小例子

  • team:设计组#member@user:张三
  • doc:海报#parent@folder:品牌
  • folder:品牌#editor@team:设计组
  • 配置：folder editor 对其子 doc 拥有 editor
    ⇒ 张三可编辑「海报」

4. 变体与扩展

  • Zanzibar 风格：关系元组存储 + 一致性与扩展性工程
  • 与 RBAC 结合：角色仍管全局功能；资源内授权走关系
  • 与 ABAC 结合：关系成立后再加环境属性条件
  • 深度/循环控制：图搜索必须有界，防性能与死循环

5. 优势

  • 贴合协作语义：成员、拥有、父子天然对应产品语言
  • 继承与嵌套优雅：减少为每个子对象复制 ACL
  • 变更局部性好：改一个「成员关系」，影响其可达资源

6. 不足与局限

  1. 心智与配置复杂：关系重写规则难写难测
  2. 调试困难：「为何能访问」需解释路径
  3. 运维成本：图数据一致性、缓存、延迟删除
  4. 不等于万能：纯岗位功能权限用 RBAC 更简单
  5. 与组织权限治理流程对接时，仍需角色/审批等上层概念

7. 在演进链中的位置

  • 旁支：不在 DAC→…→UCON 主轴替换位置上
  • 与 ACL：ACL 枚举「谁」；ReBAC 枚举「关系」并由规则推导「谁」
  • 与 ABAC：关系可看成一种结构化属性；但图可达与扁平属性策略仍是不同工具

8. 适用与不适用

更适用 更不适用
文档库、项目协作、组织树资源 仅几种全局角色的管理后台
深层嵌套与分享继承 团队无关系建模与观测能力
大规模「谁因何关系可见」 把所有 API 功能权都塞进关系图

9. 概念辨析

概念 辨析
ReBAC vs ACL 推导 vs 枚举；ReBAC 常能生成等价于大量 ACL 的效果
ReBAC vs 部门数据范围 「本部门」可用属性；「项目成员」更像关系——看领域语义选型
Zanzibar vs ReBAC 前者是后者思想的著名工业实现与论文体系

10. 小结与自测

小结

ReBAC 用关系图回答「你和资源的关系是否蕴含该操作」，特别适合协作与嵌套资源。它是细粒度旁支冠军候选，但配置与解释成本要求团队具备相应成熟度。

自测

  1. 把「项目成员可读项目下所有文档」分别用 ACL、ABAC、ReBAC 各用一句话建模，哪种最省事？
  2. 为什么调试 ReBAC 往往需要「展示证明路径」？
  3. 何种信号出现时，应从「RBAC + 部门属性」升级评估 ReBAC？

要点：1）ReBAC 最贴；2）授权由路径推出；3）大量嵌套分享/成员继承/对象图复杂。
