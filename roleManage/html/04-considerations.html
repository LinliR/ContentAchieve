04 · 角色管理考量：立项前必须想清楚的事

前置：01、02、建议已读完 models/08-comparison.md。
本章产出进入 06-outputs.md 的 O3 / O7。

1. 学习目标

读完本章，你应能：

  1. 按 A–G 分组，对一个新项目逐项写出结论（不是只勾问题）
  2. 解释每组考量如何影响模型组合与粒度
  3. 识别至少六种理论层反模式
  4. 把「不做项」写成与「做」同等重要的输出

2. 为什么需要考量清单

模型教会你「有哪些工具」；考量清单逼你问「这个项目的约束是什么」。

没有清单的典型失败：

  • 先建 user_role 表，再发现要多租户
  • 角色建了 80 个，才发现是在用角色表达部门
  • 上线前才说「工单要分享」，ACL 被迫打补丁

用法： 逐项讨论 → 把结论记入 O3 → 冲突项升为 O8 开放问题。

3. 分组精讲

A. 业务与组织

# 考量点 要得出的结论 为何重要
A1 岗位是否清晰 能否用有限角色覆盖主路径 不清晰则 RBAC 角色会假稳、真乱
A2 岗位变化频率 变更频率；是否要角色继承 高频变化要简化角色、加强流程
A3 多组织 / 多租户 租户是硬边界还是属性；隔离强度 决定 TENANT 范围与是否 L 档
A4 互斥职责 是否要 SoD（如制单 vs 审核） 约束写进角色设计，而非靠自觉
A5 外包 / 临时 / 服务账号 Subject 类型列表 漏掉服务账号会在集成时开上帝权限

理解要点： 组织不清楚时，先做组织访谈，不要先画权限表。

B. 权限范围与粒度

# 考量点 要得出的结论 为何重要
B1 功能权限边界 模块 / 菜单 / 操作 哪一级 默认操作级（见 01）
B2 是否要数据权限 SELF/DEPT/…/ALL 哪些 有则必须写 O6 语义
B3 字段级 做 / 不做 不做也要白纸黑字
B4 对象级分享 有无；哪些资源类型 有 → ACL/ReBAC 信号
B5 权限码命名 如 资源:操作，全系统统一 鉴权真源；避免菜单 ID 当权限

原则（背诵）： 角色打包功能权限；部门/租户描述数据范围；勿把部门直接当角色。

C. 模型与组合

# 考量点 要得出的结论 为何重要
C1 主模型 通常 RBAC 决策句式主语
C2 旁支 属性规则 / ACL / ReBAC / 无 防止漏场景或过度设计
C3 是否触及 UCON 吊销、义务、计量、ongoing 多数项目仅检查清单
C4 静态 vs 动态占比 能静态则优先静态 治理成本与可解释性

对照演进与决策：02、05。

D. 生命周期与治理

# 考量点 要得出的结论 为何重要
D1 角色谁创建/审批 人与流程 防「业务随便加超级角色」
D2 用户如何绑角色 自助 / 申请 / 管理员 影响审计与安全
D3 变更如何生效 立即 / 重登录 / Token 刷新 必须与业务预期一致
D4 离职/调岗回收 自动解绑、审计 权限残留是高频事故
D5 拒绝是否可解释 要/不要到什么程度 影响能否上复杂 ABAC

E. 安全与合规

# 考量点 要得出的结论 为何重要
E1 最小权限如何落地 默认拒绝 + 显式授权 底线
E2 操作审计 哪些操作必记 导出/作废/分享/改角色常入选
E3 二次确认 / 双人复核 哪些敏感操作 与角色约束配合
E4 等保/密级 是否引入 MAC 思想 有则局部强制，无则不要假装

F. 「首期不做」（防蔓延）

「不做」与「做」同级，写入 O7。建议起步勾选：

  • 字段级权限
  • 非白名单资源的对象级 ACL
  • 完整 ABAC 策略引擎
  • UCON ongoing / 计量平台
  • 全站 MAC
  • 其他：________

理解要点： 不做项是范围控制工具，不是偷懒；O9 写清「什么信号才允许推翻不做项」。

G. 反模式（理论层）

# 反模式 后果 纠正
1 一用户一专属角色 RBAC 名存实亡 合并职责为共享角色
2 部门 = 角色 功能/数据搅死、角色爆炸 部门→范围；角色→权限包
3 权限大量直绑用户 无法治理 走角色指派
4 为每条数据建角色 运维崩溃 范围规则或 ACL
5 无治理上完整 ABAC 策略失控 先 RBAC+有限规则
6 无过程需求却上 UCON 过度设计 UCON 作检查清单
7 菜单 ID 当权限码 重构 UI 就鉴权崩 资源:操作 稳定符号
8 默认允许 违背最小权限 默认拒绝

4. 如何开一场「考量会」（实践）

建议 60–90 分钟，参与：业务负责人、系统分析、开发代表。

  1. 投影 A–E 表，逐项只允许输出结论句
  2. 争议项记入「开放问题」草稿（后入 O8）
  3. 会结束前填写 F 不做项（全体确认）
  4. 会后整理进 O3，不当场选框架

5. 与交付物的映射

考量组 主要进入
A–E 结论 O3
F O7
争议 O8
C 的模型倾向 O2（最终句式在 05 定稿）

6. 小结与自测

小结

考量清单把「模型知识」变成「项目约束」。
逐项要结论；不做项要白纸黑字；反模式用于评审拍砖。

自测

  1. 为什么 A3（租户）答「有」时，不能只加一个角色叫「租户管理员」了事？
  2. B4 出现「工单可分享给个人」时，C2 应倾向什么？为何不是新建角色？
  3. 举一个「不做项」在三个月后被错误推翻的故事，并说明 O9 本该怎么写。
  4. 用 G 中两条反模式，检查你上一个系统（或澄单案例）。
