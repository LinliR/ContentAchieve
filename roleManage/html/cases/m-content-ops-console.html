案例 · 内容运营管理后台（档位 M）

性质：虚构教学案例，用于示范理论交付物如何填写。
档位：M · 标准企业应用（见 ../05-decision-framework.md）
主模型组合：RBAC（功能）+ 轻量属性规则（数据范围）
术语：以 ../glossary.md 为准

0. 项目背景（给定输入）

某中型内容团队需要建设「内容运营管理后台」，支撑稿件从创建到发布的日常工作。

已知事实：

  • 岗位相对清晰：编辑、运营、审核、管理员
  • 组织有部门（如「资讯中心」「视频中心」），编辑主要处理本部门内容
  • 需要菜单/按钮/接口级功能权限
  • 存在「本人稿件 / 本部门稿件 / 全部稿件」的数据范围诉求
  • 首期没有「把单篇稿件分享给任意同事」的强需求
  • 无密级标密制度；非多租户 SaaS
  • 无「播放中途吊销、计量额度、强制同意协议后继续用」等使用过程控制需求
  • 团队希望权限模型可讲清、可审计，避免一上来上策略引擎

决策树速答（对照 05）：

问题 答案 倾向
Q1 岗位 vs 分享 以岗位能力为主 RBAC
Q2 属性/环境 要本部门/本人 RBAC + 数据范围规则
Q3 使用过程 请求级鉴权即可 不引入 UCON 平台
Q4 粒度 操作级；不做字段级 停在操作

⇒ 档位 M。

O1 · 问题框架

  • Subject 类型：内部员工账号（自然人）；首期不含外部服务账号开放 API
  • Object 类型：二者皆有——功能（菜单/API）为主鉴权对象；业务对象（稿件、栏目）作为数据范围作用对象
  • 主要 Action：查看、创建、编辑、提交审核、审核通过/驳回、发布、下线、导出
  • Context：部门；工作时间不作硬性鉴权条件（首期）
  • 功能权限：要
  • 数据权限：要；形态 = SELF / DEPT / ALL（见 O6）

四元组例句：

用户（编辑·资讯中心）对 稿件 执行 编辑，在「本部门数据范围」下，是否允许？

O2 · 模型选型

  • 主模型：RBAC
  • 旁支组合：轻量属性规则（数据范围）；首期无 ACL / 无 ReBAC / 无全站 MAC / 无 UCON 平台
  • 档位：M
  • 理由（对照演进线）：
    • 需求落在「企业岗位授权」→ RBAC
    • 「本部门/本人」超出纯静态角色组合舒适区，但规则少且固定 → 用数据范围规则（ABAC 思想），不上完整策略引擎
    • 无对象级随意分享 → 暂不引入 ACL/ReBAC
    • 无使用中控制 → UCON 仅作检查项，结论为「不需要」

决策句式：

本项目以 RBAC 为主模型；
因存在部门与本人数据隔离，补充 SELF/DEPT/ALL 数据范围规则（轻量 ABAC）；
功能权限粒度到 操作级；数据权限采用 本人/本部门/全部；
首期明确不做 字段级权限、对象级 ACL、完整 ABAC 引擎、UCON ongoing。
对照演进线：岗位稳定，主要停在 RBAC 阶段，局部借用 ABAC 思想；未达完整 ABAC/UCON 必要度。

O3 · 关键考量结论

完整项对照 ../04-considerations.md；此处给出结论摘要。

编号 结论
A1 岗位清晰度 清晰，可用有限角色覆盖主路径
A2 岗位变化频率 中低；角色继承首期不做，避免理解成本
A3 多组织/多租户 单组织多部门；无租户
A4 互斥职责 编辑与终审宜分离：同一用户不可同时拥有「提交人终审自己稿」的闭环（见 O5 约束与 O8）
A5 Subject 类型 仅内部员工
B1 功能粒度 操作级权限码
B2 数据范围 SELF / DEPT / ALL
B3 字段级 首期不做
B4 对象分享 首期不做
B5 权限码规则 资源:操作，小写，冒号分隔
C1 主模型 RBAC
C2 旁支 仅数据范围规则
C3 UCON 检查后不需要平台
C4 静/动态 功能静态绑定；数据范围少量动态规则
D1 角色谁维护 管理员维护角色与指派；安全相关变更记审计
D2 绑角色流程 管理员分配；首期无自助申请流
D3 变更生效 重新登录后生效（简单可讲清）；开放问题见 O8
D4 离职回收 账号停用 + 解绑角色；须可审计
D5 拒绝可解释 需要；故避免黑盒策略引擎

O4 · 权限对象清单（逻辑）

逻辑名与权限码，非表结构。可迭代增补。

资源（逻辑名） 操作 权限码 备注
稿件 查看 article:view
稿件 创建 article:create
稿件 编辑 article:edit 受数据范围约束
稿件 删除 article:delete 敏感
稿件 提交审核 article:submit
稿件 审核 article:review 通过/驳回
稿件 发布 article:publish 敏感，须审计
稿件 下线 article:unpublish 敏感
稿件 导出 article:export 敏感，须审计
栏目 查看 category:view
栏目 管理 category:manage 增删改栏目
用户 查看 user:view
用户 管理 user:manage 含角色指派
角色 查看 role:view
角色 管理 role:manage 改角色权限包
审计日志 查看 audit:view

菜单可见性由上述权限码推导，不另设「仅菜单权」——避免双源真相。

O5 · 角色初稿

角色 职责简述 权限包 数据范围默认 约束
编辑 撰写与改稿、提交审核 article:view,create,edit,submit；category:view SELF 不能审核/发布
运营 本部门内容运营、发布与下线 编辑权限包 + article:publish,unpublish,export；category:view DEPT 不能 user:manage / role:manage
审核 审核稿件 article:view,review；category:view DEPT 不可审核自己提交的稿件（SoD，见 O8）
管理员 账号、角色、栏目与全局内容应急 显式列举：上述全部权限码 ALL 账号须受控；操作全审计

说明：

  • 不用 运营_资讯中心 这种角色名承载部门——部门来自用户属性 + DEPT 规则。
  • 同一人可绑「编辑 + 运营」，但「编辑 + 审核」触发 SoD 规则（开放问题落地前，管理上先禁止双绑）。

O6 · 数据范围规则

范围名 语义 含下级部门？ 适用
SELF 仅 creator_id = 当前用户 的稿件（负责字段若有，可并列「负责人=当前用户」，首期只做创建者） — 编辑默认
DEPT 稿件所属部门 = 用户部门 否（首期不含下级；若组织有子部门，二期再开「含下级」开关） 运营、审核默认
ALL 不按部门过滤 — 管理员

判定顺序（逻辑）：

  1. 先过功能权限（RBAC 权限码）
  2. 再过数据范围（对本条/本列表过滤）
  3. 默认拒绝

歧义已拍板：DEPT 不含下级——写进方案，避免上线后争议。

O7 · 首期范围与不做项

做：

  • RBAC 角色与权限码（O4/O5）
  • SELF / DEPT / ALL 数据范围（O6）
  • 权限变更与敏感操作审计
  • 管理员维护角色指派

不做：

  • 字段级权限
  • 对象级 ACL（单篇分享）
  • ReBAC
  • 完整 ABAC 引擎 / 外置策略语言
  • UCON ongoing / 义务框架
  • 角色继承树
  • 多租户
  • 密级 MAC

O8 · 风险与开放问题

问题 影响 计划何时定
「审核不可审自己的稿」是管理禁止双绑，还是系统强制校验？ SoD 强度与实现复杂度 一期开发前拍板；建议系统强制
权限变更是否支持「立即生效」而不只重新登录？ 安全窗口 vs 实现成本 二期评估
运营是否需要「跨部门只读」例外？ 可能冲击 DEPT 模型 有真实工单再开，避免预支
导出是否要审批流？ 产品流程，非模型升级 产品定；模型仍用 article:export

O9 · 演进预留

  • 出现 「单篇稿件分享给指定人只读/可编」且频率高 → 评估引入 ACL（仅稿件资源类型）。
  • 出现 跨部门复杂条件、时间窗、设备约束大量入策，角色开始爆炸 → 评估 完整 ABAC / 策略治理配套。
  • 出现 会话中吊销、导出前强制同意、计量额度 → 用 UCON 检查表逐项落地局部机制，仍不必先上「UCON 平台」。
  • 出现 正式密级与强制不可分享 → 评估局部 MAC 思想（标签 + 强制策略）。

教学点评（读完案例后看）

  1. 档位 M 的关键：不是「功能很多」，而是「RBAC + 固定少数数据范围」。
  2. 故意不做 ACL：避免教学案例变成「什么都上一点」；预留写在 O9。
  3. DEPT 不含下级 展示了理论输出必须消歧，否则实现阶段必返工。
  4. SoD 说明约束可以先以「开放问题 + 管理措施」存在，但应尽快变成系统规则。
  5. 对照 ../models/08-comparison.md 口诀：本案例即「RBAC 打底，属性管范围，分享与持续按需不加」。
