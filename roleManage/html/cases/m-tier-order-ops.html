案例 M · 制造企业「订单与售后」运营后台

0. 业务背景（决策输入）

华澄制造准备自建内部系统「澄单」（ChengOrder）：

  • 用户约 80～150 人：销售、售后、仓储、财务、系统管理员
  • 单租户、有部门树（销售一部/二部、售后中心、仓储、财务、IT）
  • 核心对象：客户、订单、发货单、售后工单、基础资料
  • 明确诉求：
    • 按岗位控制菜单与操作（谁能建单、谁能作废、谁能导出）
    • 销售只能看本部门订单；销售经理看本部门及下级；财务/管理员看更多
    • 个别售后工单需要临时分享给其他部门某人只读协作
  • 明确不做（业务已口头确认）：字段级权限、跨公司多租户、视频类持续播放控制、密级标密

决策树速答（Q1–Q4）

问 答 倾向
Q1 岗位还是分享？ 以岗位为主，分享是少数工单 RBAC 为主 + 少量 ACL
Q2 属性/环境？ 部门数据隔离强 RBAC + 数据范围（轻量 ABAC）
Q3 使用过程？ 请求级鉴权即可 不引入 UCON 平台
Q4 粒度？ 操作级；不做字段级 停在操作级

→ 落在 档位 M。

O1 · 问题框架

  • Subject 类型：内部员工账号；首期不含外部客户门户、不含机器服务账号（开放问题见 O8）
  • Object 类型：二者皆有
    • 功能对象：菜单、按钮、API 操作
    • 业务对象实例：订单、售后工单（实例分享仅工单）
  • 主要 Action：view / create / update / cancel（作废）/ export / assign（分派）/ close（结案）/ share（分享，仅工单）
  • Context：部门（组织树）、是否在职；首期不考虑时间窗与设备指纹
  • 功能权限：要
  • 数据权限：要；形态 = SELF / DEPT / DEPT_AND_CHILD / ALL（定义见 O6）

O2 · 模型选型

  • 主模型：RBAC
  • 旁支组合：
    • 数据范围 = 轻量属性规则（ABAC 思想，非完整策略引擎）
    • 售后工单临时协作 = 对象级 ACL（白名单资源类型仅 ticket）
  • 档位：M
  • 理由（对照演进线）：岗位清晰，落在 RBAC 阶段；部门隔离触及 ABAC 思想；少数实例分享用 ACL 旁支。无密级强制（不做 MAC），无使用中吊销/计量（不做 UCON 平台）。

决策句式：

本项目以 RBAC 为主模型；
因存在部门数据隔离，补充 SELF / DEPT / DEPT_AND_CHILD / ALL 范围规则（轻量 ABAC）；
因个别售后工单需临时协作，补充 仅 ticket 资源的对象级 ACL；
功能权限粒度到 操作级；
首期明确不做 字段级权限、完整 ABAC 引擎、ReBAC、全站 MAC、UCON ongoing。
对照演进线：需求主要落在 RBAC，局部触及 ABAC 思想与 ACL 旁支，未达完整 ABAC/UCON 必要度。

O3 · 关键考量结论

依据 04-considerations.md，摘要如下（完整可作附表）。

编号 结论
A1 岗位清晰度 高：销售/售后/仓储/财务/管理员可枚举
A2 岗位变化频率 中低：季度调岗；角色绑定由管理员维护
A3 多组织/租户 单租户；部门树 2～3 层
A4 互斥职责 需要：销售「创建订单」与财务「订单作废终审」互斥（见 O5 约束）
A5 主体类型 首期仅内部员工
B1 功能粒度 操作级权限码；菜单由权限码驱动显示
B2 数据范围 SELF / DEPT / DEPT_AND_CHILD / ALL
B3 字段级 不做
B4 对象分享 仅售后工单；订单不做分享
B5 权限码规则 资源:操作，小写英文，见 O4
C1 主模型 RBAC
C2 旁支 数据范围规则 + ticket ACL
C3 UCON 仅作检查：无 ongoing / 义务硬需求
C4 静态 vs 动态 功能静态绑定；数据范围动态按部门属性
D1 角色谁建 IT 管理员创建角色；业务负责人书面确认权限包
D2 绑角色流程 管理员分配；调岗工单驱动
D3 变更生效 重新登录后生效（首期约定，简单可预期）
D4 离职回收 账号停用即失效；ACL 条目中主体停用视为无效
D5 拒绝可解释 功能拒绝提示「无权限」；数据拒绝不暴露其他部门存在性（列表直接过滤）
E1 最小权限 默认拒绝；新角色空权限起步
E2 审计 导出、作废、分享、角色变更写审计日志
E3 敏感操作 订单作废需财务角色；首期不做双人复核（开放见 O8）
E4 密级 无
F 不做项 见 O7

O5 · 角色初稿

角色码 名称 职责简述 权限包 默认数据范围 约束
sales 销售 维护客户、创建与修改本部门订单 customer:*（无 export）, order:view/create/update, ticket:view/create DEPT 不可 order:cancel
sales_mgr 销售经理 销售权限 + 看下级部门 + 导出 含 sales 全部 + customer:export + order:export DEPT_AND_CHILD 不可 order:cancel
cs 售后 工单处理与结案 ticket:view/create/assign/close/share, order:view, customer:view DEPT —
warehouse 仓储 发货 shipment:*, order:view ALL（发货需跨部门看单，但仅发货相关） 不可改订单金额类操作（本系统无该权限码）
finance 财务 作废终审、导出、审计只读 order:view/cancel/export, customer:view/export, admin:audit ALL 与 sales / sales_mgr 互斥
admin 系统管理员 账号角色与审计 admin:* + 只读业务 view 便于排障 ALL 不授予日常 order:cancel（避免身兼财务）

说明：

  • 权限包用「角色码 → 权限码列表」维护；上表为初稿粒度。
  • warehouse 的 ALL 仅因发货协同；若日后滥用，可改为「关联本仓订单」自定义范围（演进见 O9）。
  • 互斥：同一用户不可同时拥有 finance 与 sales/sales_mgr。

O6 · 数据范围规则

范围名 语义（写死，防歧义） 适用
SELF 业务记录的 owner_id 或 created_by = 当前用户 预留；首期角色默认不用，个人草稿可走业务状态
DEPT 记录的 dept_id = 用户主部门 dept_id；不含下级部门 sales, cs
DEPT_AND_CHILD dept_id ∈ 用户主部门及其组织树全部下级 sales_mgr
ALL 单租户内全部数据（本系统无多租户） finance, admin；warehouse 对发货/订单查看
ACL_GRANT 非范围枚举值：对象 ACL 显式授予的 ticket 可读，即使不在部门范围内 与范围规则 并集：范围命中 或 ACL 命中即可 view

判定顺序（逻辑）：

  1. 先过功能权限（无 ticket:view 直接拒绝）
  2. 再：数据范围命中 OR（资源为 ticket 且 ACL 允许该操作）
  3. 列表接口：过滤不可见行，不返回「无权限」明细以免探测

部门树约定：

  • 用户仅一个主部门；兼职部门首期不做（开放 O8）
  • 部门调整次日或重新登录后范围生效（与 D3 一致）

O7 · 首期范围与不做项

做

  • RBAC 操作级权限 + 角色可配置
  • 四档数据范围 + ticket ACL 分享（只读为主，分享权限可含 view；首期分享不授予 close）
  • 角色互斥（财务 vs 销售）
  • 敏感操作审计：export / cancel / share / 角色变更
  • 权限变更：重新登录生效

不做

  • 字段级权限
  • 订单等非 ticket 资源的对象级 ACL
  • 完整 ABAC / 策略引擎 / 策略语言
  • ReBAC / 关系图授权
  • 全站 MAC / 密级标签
  • UCON ongoing、计量、使用中强制义务
  • 多租户
  • 用户多主部门 / 兼职范围
  • 双人复核作废
  • 对外客户门户账号

O8 · 风险与开放问题

问题 影响 计划何时定
仓储 ALL 是否过宽 可能看到非本仓订单详情 上线后 1 个月内用访问审计评估；必要则改 CUSTOM
作废是否要双人复核 财务舞弊面 二期合规评审
服务账号（对接 ERP） Subject 类型扩展 与 ERP 对接立项时一并设计
兼职多部门 范围语义复杂 业务提出兼职需求时再开
ACL 分享是否允许「可编辑」 扩大协作面与风险 首期只读；二期评估
权限变更改为即时生效 体验 vs 会话缓存复杂度 工程方案阶段评估，理论阶段维持重登录

O9 · 演进预留

  • 出现 大量非工单对象的临时分享 / 深层文件夹式继承 时，再评估引入 ReBAC（或扩展 ACL 资源类型）。
  • 出现 跨部门复杂条件组合、风险分、时间窗策略、多属性组合导致角色爆炸 时，再评估 完整 ABAC / 策略引擎（须同步策略测试与拒绝原因）。
  • 出现 导出配额、会话中强制下线、同意条款后才继续敏感操作且需中途可撤 时，再评估 UCON 思维落地（义务 + ongoing）。
  • 出现 法定密级 / 强制隔离红线 时，再评估局部 MAC 标签。
  • warehouse 范围过宽的信号：审计显示大面积跨部门详单访问 → 优先上 CUSTOM 数据范围，仍不必上完整 ABAC。

附录 · 给学习者的对照提示

写自己的项目时，重点抄结构，不抄角色名：

  1. 决策树四问是否都有书面答案
  2. 数据范围是否消除「含不含下级」歧义
  3. ACL 是否白名单资源类型，避免全站 ACL 化
  4. 互斥与审计是否写在角色表旁，而不是事后补丁
  5. O9 是否写清「什么信号才升级模型」，避免提前过度设计
