06 · 理论输出：进入编码前必须交付什么

前置：01–05 与模型对照章。
空白模板用于真实项目；填写范例见 cases/。
先独立填写，再看案例。

1. 学习目标

读完并练完本章，你应能：

  1. 说出 O1–O9 各自解决什么问题、缺谁不能开工
  2. 独立完成一份理论立项（不写代码、不写 DDL）
  3. 用验收标准判断「理论阶段是否结束」
  4. 解释为何交付物是逻辑设计而非框架配置

2. 为什么要有「理论交付物」

没有书面输出时，常见现象：

  • 口头说「做 RBAC」，桌上却是部门当角色
  • 开发已建表，业务才说「要分享工单」
  • 「部门含不含下级」每个人理解不同

交付物把理解钉在纸上，使评审可拍板、工程可接手。

懂模型 ≠ 项目可开工
可开工 = 模型选型 + 约束结论 + 权限/角色/范围初稿 + 不做项 已书面化

3. 交付物清单（O1–O9）

ID 交付物 必须？ 解决的问题 主要依据
O1 问题框架说明 必须 判定什么 01

O3 考量结论表 必须 项目约束是什么 04
O4 权限对象清单（逻辑） 必须 有哪些权限码 01 粒度 + 业务清单
O5 角色初稿与职责 必须 谁有哪些包 RBAC 专章 + 业务岗位
O6 数据范围规则 有数据权限时必须 范围语义无歧义 01 §4、glossary 范围名
O7 首期做/不做 必须 防蔓延 04-F、05-Q4

全部为理论 / 逻辑设计。框架、中间件、DDL → 后续工程分册。

依赖顺序（写作时）

O1 → O3 → O2（选型句式）→ O4/O5 → O6（若需要）→ O7 → O8/O9

O2 也可与 O3 穿插，但决策句式应在考量有结论后定稿。

4. 每一项「写好」的标准（教材级）

ID 写好的样子 不及格的样子
O1 四元组有值；功能/数据是否要写死 只写「做权限」
O2 有档位 + 完整决策句式 + 演进对照一句 只写「用 RBAC」
O3 A–F 有结论句，不是复述问题 大段空白或「待定」过多
O4 资源×操作表；权限码稳定 只有菜单截图
O5 角色、职责、权限包、约束（互斥等） 角色名无权限包
O6 DEPT 是否含下级等写死；与功能权关系写清 「按部门控制」一句话
O7 做与不做两列都有 只有愿望清单
O8 问题、影响、计划何时定 空表或发泄式吐槽
O9 「出现信号 X 再评估模型 Y」 「以后再优化」

6. 验收标准（理论阶段 DoD）

理论阶段可结束、进入实现方案，当且仅当：

  1. O1–O3、O7 已填写且评审通过
  2. O4、O5 有可迭代初稿（允许后续增删权限码）
  3. 若有数据权限，O6 语义清晰（含组织树歧义点）
  4. 决策句式能向非安全背景业务方讲清「为什么这样选」

未达标 → 回 01/04/05，不进入工程分册。

7. 练习法（理解用）

  1. 打印或复制本章模板
  2. 任选：你的真实项目，或自编「10 人小后台」
  3. 不看 cases，限时 90 分钟填完
  4. 再打开同档案例对照，列出差异 ≥3 条并写理由
  5. 用 §6 四条打勾

9. 小结与自测

小结

O1–O9 把「我懂了」变成「项目可交接」。
写好标准比填满格子更重要；O6/O7/O9 最能检验真理解。

自测

  1. 为什么没有 O7 也可以「看起来像」写完方案，却仍危险？
  2. O4 为什么禁止用菜单标题代替权限码？
  3. O2 与 O3 谁先谁后？若冲突怎么办？
  4. 理论 DoD 四条，删掉哪一条最容易导致工程返工？

要点： 1）范围会蔓延；2）UI 变权限崩；3）先约束后定稿句式，冲突回评审；4）常是 O6 歧义或 O7 缺失。
