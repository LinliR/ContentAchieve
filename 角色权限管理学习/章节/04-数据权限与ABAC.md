# 第 4 章：数据权限与 ABAC

掌握深度：**重点掌握基础应用**。先回顾：有 article:update 为什么还不能修改任意文章？

## 概念摘要

ABAC 将主体、资源、操作和环境的属性代入策略。例如“当前用户部门等于文章部门，文章处于待审核状态，并且用户具有审核权限”。属性本身不产生权限，规则才赋予它意义。

数据权限表达可操作的记录范围。本人、所属部门、指定部门和全部数据都是常见范围，但这些是业务约定，不是数据库自动提供的保护。

## 从自然语言到条件

“编辑只能审核本部门的待审核文章，而且不能审核自己的文章”可以写成：

```text
允许审核 = 具有审核权限
        AND 当前用户部门 == 文章部门
        AND 文章状态 == PENDING
        AND 当前用户 ID != 文章作者 ID
```

用户 ID 与部门来自服务端认证身份和账号记录；文章作者、部门、状态来自数据库。不能让客户端传入 `isEditor=true` 或 `departmentId=目标部门` 就通过校验。关键属性缺失时拒绝，不把 null 当作“所有部门”。

## 不同接口要保持一致

| 操作 | 正确思路 |
|---|---|
| 列表与分页 | 在查询条件中加入范围，然后计数、排序和分页 |
| 详情 | 通过同样范围定位 id，不能只按 id 查询后直接返回 |
| 修改与删除 | 在授权范围内定位记录，再校验业务状态 |
| 批量与导出 | 每条记录遵守相同范围；不能只检查第一个 id |

先查全部记录再在 Java 中过滤，容易泄漏总数、破坏分页，也会扩大敏感数据读取范围。对本课程的小项目，使用 JPA Specification 把条件推入数据库。

## 多角色范围如何组合

本案例每个角色有 OWN、DEPARTMENT、ALL 之一。计算某操作的范围时，仅合并**同时授予该操作**的有效角色的范围。

例如：角色 A 允许全部阅读，角色 B 允许本人修改。阅读范围为 ALL，修改范围为 OWN。不要先合并所有角色范围再套到每个操作上。

随后再与项目成员条件取交集。ALL 表示部门/归属维度不限制，不代表绕过项目关系或业务状态。

## 易错点

- 将范围和操作权限独立合并，意外放大权限。
- 列表做了范围过滤，详情或导出没有做。
- 信任请求中的部门、作者或状态来进行授权。
- 把 `OR` 与 `AND` 写错，导致任一条件成立就放行。

## 自测

1. 已经校验角色，为什么列表仍要过滤？
2. 用户可读全部文章、可改本人文章，能否修改同事文章？
3. 文章从 PENDING 变为 APPROVED 后，原审核条件是否仍成立？

<details><summary>自测答案</summary>

1. 角色解决功能或范围来源，必须把结果应用到具体查询。
2. 不能，范围要绑定操作计算。
3. 不成立；状态是动态条件，需要按最新记录判断，并考虑并发变更。

</details>
