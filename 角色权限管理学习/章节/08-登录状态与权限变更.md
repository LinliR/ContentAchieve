# 第 8 章：登录状态、权限变更与越权

掌握深度：**重点掌握**。先回顾：撤销角色后，为什么还要检查下一次请求的行为？

## 概念摘要

| 术语 | 职责 | 不应推导出的结论 |
|---|---|---|
| Cookie | 浏览器保存并按规则发送的小段数据 | Cookie 天然安全，或只用于登录 |
| Session | 服务端维护会话状态，通常由会话标识关联请求 | Session 中的权限永远是最新的 |
| Token | 代表某种声明或访问资格的凭据统称 | 所有 Token 都是 JWT |
| JWT | 一种声明表示格式，常使用签名验证完整性 | 签名使内容保密，或能自动解决撤权 |

常见的签名 JWT 内容可以被解码，不能放入密码等秘密。是否采用 Session、JWT，以及如何验证发行者、受众和有效期，是认证与凭据设计；不替代角色、资源范围和关系检查。

## 业务例子：撤权后仍能访问

用户登录时，系统把 `article:review` 保存到 Session 或 Token。管理员撤销编辑角色，但请求仍使用旧的权限快照，所以仍可能访问。

解决思路包括：每次查询最新授权、权限版本校验、可靠的缓存失效或会话失效。仅缩短 Token 有效期只能缩短旧权限存续窗口，不能等价于立即撤权。

本项目选择容易验证的方式：Session 保存身份，每次请求刷新账号状态和有效权限，资源关系也实时查询。代价是增加数据库访问，适合学习职责和正确性，暂不引入缓存。

## 越权的两种典型情况

- **水平越权：** 作者将文章 id 从自己的改为其他作者的，接口仍允许修改。
- **垂直越权：** 普通作者直接调用角色分配接口，为自己赋予管理员角色。

校验参数格式只能判断 id 是否合法，不能判断用户是否有权访问对应记录。

## 会话与 CSRF

浏览器会自动携带符合条件的 Cookie，所以基于 Cookie 的登录要考虑跨站请求伪造。学习项目保留 Spring Security 的 CSRF 防护：先取得 CSRF token，再在登录和修改请求中发送；登录后重新获取 token。不要为了让接口工具方便而全局关闭保护。

## 变更日志与边界

记录谁在什么时候修改了哪个用户的角色、哪个角色的权限或哪个成员关系，便于解释授权变化。不记录明文密码和会话凭据。

本项目记录成功的授权变更及文章操作，不提供完整的拒绝事件分析平台，也不实现分布式会话撤销。

## 易错点

- 将 Token 中的权限快照当作实时授权事实。
- 仅清理某一台服务的缓存，却承诺所有请求立即撤权。
- 只检查资源 ID 格式，不校验该身份与资源的访问关系。
- 记录完整会话凭据或密码作为排错信息。

## 自测

1. 用户被停用，但旧 Session 仍存在，能否仅根据 Session 放行？
2. JWT 验签通过，能否说明其中的权限仍然有效？
3. 撤销一个角色后，该用户一定失去该角色包含的全部权限吗？

<details><summary>自测答案</summary>

1. 不能。需要检查账号当前状态或让相关会话可靠失效。
2. 不能。验签证明签名和内容完整性，权限还可能因业务变更过时。
3. 不一定，其他有效角色可能授予同一权限。

</details>
