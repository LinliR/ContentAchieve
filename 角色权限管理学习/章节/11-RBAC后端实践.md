# 第 11 章：完成 RBAC 后端

掌握深度：**重点掌握**。前提：完成第 10 章的独立设计。

## 概念摘要

本章将角色与权限落实为可调用的服务。参考项目提供最终实现，学习时分步阅读和操作，不需要一开始通读所有文件。

## 第一步：启动与登录

按 [项目说明](../实践项目/README.md) 选择 Java 21，运行测试和服务。打开 [接口请求示例](../实践项目/requests.http)。先取得 CSRF token，再登录，然后重新获取 token。

观察：登录解决身份问题；登录后请求 `/api/auth/me` 可以看到当前有效权限，但这些信息不是前端自行宣布的。

## 第二步：先读表关系

阅读 UserAccount、AppRole、AppPermission 与 Repositories，和第 3 章的五张表对照。实体不直接作为 HTTP 响应，ApiTypes 定义返回字段，避免将密码散列和无关关联序列化出去。

角色上的 scope 是教学案例的数据范围扩展，可先知道含义，到下一章再分析查询实现。

## 第三步：完成角色管理流程

使用管理员身份按顺序操作：

1. 创建一个空权限角色。
2. 查询权限字典，为角色配置 article:read。
3. 创建一个普通用户，将角色分配给他。
4. 让该用户登录，观察功能权限与文章范围。
5. 保持用户原会话，修改或撤销角色权限，再次请求。
6. 尝试删除仍被引用的角色，应返回 409；解除用户角色分配后再删除。

把每一步的预期结果先写下，再发请求。不知道文章为什么为空时，先检查数据范围和项目关系，不要直接授予管理员。

## 第四步：跟踪代码路径

Controller → AdminService → Repository 是管理操作路径。SecurityConfig 和 IdentityService 负责认证上下文及权限刷新；AdminService 的方法注解保护管理能力。

普通用户调用角色分配接口应失败。仅仅将管理员按钮从前端隐藏并不能达成这个结果。

## 自己动手

在不复制完整答案的前提下，新建“审计查看者”角色，只授予 audit:read，分配给一个测试用户。确认他能查看审计，但不能编辑角色或用户。

## 易错点

- 创建了权限记录，但没有给业务方法添加对应检查。
- 只在登录时加载权限，未处理后续权限变更。
- 向客户端返回完整 UserAccount 实体。
- 删除角色时静默移除全部用户关联，导致影响范围难以追踪。

## 自测

1. 为什么 `/api/roles` 也需要管理权限？
2. 新用户获得 article:read 后文章列表为空，可能有哪些原因？
3. 怎样证明撤权不依赖重新登录？

<details><summary>自测答案</summary>

1. 角色配置本身是管理信息，本项目将读取和修改都归入 role:manage。
2. 没有项目成员关系，或者该操作范围内没有文章；也要检查角色是否有效。
3. 保留同一个用户会话，由另一个管理员会话撤权，然后用原会话重新请求并核对结果。

</details>

## 本章验收

独立创建、分配、调整、停用和删除角色，能解释返回结果；普通用户无法自行提权。
