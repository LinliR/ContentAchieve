# 第 6 章：DAC、MAC 与 ACL 的适用边界

掌握深度：**建立认识**。本章不安排独立系统实现。

## 概念摘要

**DAC**强调授权控制权：资源所有者可以在系统允许的范围内，将访问权限授予其他主体。“作者只能修改自己的文章”只检查归属，并不能单独证明系统采用 DAC；允许作者决定分享对象才体现自主授权。

**ACL**是记录授权的一种机制。例如文档 101 的授权列表：

| 主体 | 操作 |
|---|---|
| 小林 | READ、EDIT |
| 小王 | READ |

ACL 不必支持继续转授，也不能默认分享对象可再次分享；这些都需要额外规则。

**MAC**强调普通用户不能自行改变的系统强制策略，安全标签是典型表达。强制策略可能涉及级别、类别以及信息流限制，不只是比较一个整数。一个叫“超级管理员”的角色不等于 MAC。

## 业务例子：分享是否足够

文档所有者给小王配置了读取授权，但组织强制策略不允许小王接触该文档的安全类别。在组合设计中，可以要求两项都满足，所有者分享不能自动绕过强制约束。

这说明 DAC、MAC、RBAC 等并非必须五选一，也不是“后来出现的模型淘汰前面的模型”。应先明确决策权、控制依据和组合规则。

## 易错点

- 将“默认只有本人可读”直接称为自主授权。
- 将管理员角色的高权限称为强制访问控制。
- 给模型画一条从落后到先进的升级路线。
- 看到 ACL 就认为已经有完整的分享、继承和撤权机制。

## 自测

1. 用户能编辑自己的文档，但不能授权给别人，是否足以说明是 DAC？
2. 资源的 ACL 允许访问，是否可以绕过系统强制规则？
3. 学习普通 Java 后台是否必须实现 MAC 系统？

<details><summary>自测答案</summary>

1. 不足以，需要观察谁有权决定向他人授权。
2. 不可以默认绕过，要按系统定义的组合策略决策。
3. 不必。先理解概念与边界，真正有该需求时再深入专门机制。
